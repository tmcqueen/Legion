# UUID v7 Branded Primary Keys — Design Spec

**Date:** 2026-04-30
**Project:** Brigade.Admin.Data.Models + Brigade.Admin.Data
**Status:** Approved
**Prerequisite for:** All new feature work (Markdown Import System, etc.)

---

## Overview

All Brigade models currently use `int` primary keys and foreign keys. This migration replaces every `int Id` with a branded `readonly record struct` backed by UUID v7 (`Guid.CreateVersion7()`).

**Why UUID v7 over sequential int:**
- Time-ordered — avoids B-tree index fragmentation caused by random GUIDs
- Distributed-safe — IDs can be generated client-side without a database round-trip
- No information leakage — doesn't expose row counts or insertion order to end users

**Why branded structs over plain `Guid`:**
- Compile-time type safety — the compiler rejects `ProviderOptionsId` where `AgentOptionsId` is expected
- Self-documenting — `AgentOptionsId` is unambiguous in any context
- Zero-cost at runtime — `readonly record struct` has no heap allocation

**Auth tables (Identity + OpenIddict) are excluded** — they already use `string` GUIDs managed by ASP.NET Core Identity and are not touched by this migration.

## Branded ID Convention

### Pattern

Each entity gets its own `readonly record struct` ID type. All ID types follow this template:

```csharp
readonly record struct AgentOptionsId(Guid Value)
{
    public static AgentOptionsId New() => new(Guid.CreateVersion7());
    public static implicit operator Guid(AgentOptionsId id) => id.Value;
    public static implicit operator AgentOptionsId(Guid value) => new(value);
    public override string ToString() => Value.ToString();
}
```

### Placement

All ID types live in a single file: `Brigade.Admin.Data.Models/Ids.cs`

### EF Core Value Converter Registration

Each ID type requires a value converter registered in `OnModelCreating`. A shared helper avoids repetition:

```csharp
// Brigade.Admin.Data/Configurations/IdConventionExtensions.cs
public static class IdConventionExtensions
{
    public static void RegisterIdConverter<TEntity, TId>(
        this ModelBuilder builder,
        Expression<Func<TEntity, TId>> keyExpression,
        Func<Guid, TId> fromGuid)
        where TEntity : class
    {
        builder.Entity<TEntity>()
            .Property(keyExpression)
            .HasConversion(id => ((Guid)(object)id), value => fromGuid(value));
    }
}
```

In practice, each configuration class calls e.g.:
```csharp
builder.Property(e => e.Id)
    .HasConversion(id => id.Value, value => new AgentOptionsId(value));
```

## Migration Strategy

Since changing a primary key column type requires dropping and recreating all foreign keys and the column itself, the cleanest approach is to **wipe all existing `App` migrations and generate a fresh initial migration**.

**Steps:**

1. Delete all migration files under:
   - `Brigade.Admin.Data.PostgreSQL/Migrations/App/`
   - `Brigade.Admin.Data.Sqlite/Migrations/App/`
   - (Leave `Auth/` migrations untouched — Identity tables are not changing)

2. Make all model and configuration changes described above.

3. Regenerate the App initial migration for both providers:
   ```bash
   dotnet ef migrations add InitialCreate \
     --project Brigade.Admin.Data.PostgreSQL \
     --context AppDbContext \
     --output-dir Migrations/App

   dotnet ef migrations add InitialCreate \
     --project Brigade.Admin.Data.Sqlite \
     --context AppDbContext \
     --output-dir Migrations/App
   ```

4. Review both generated migrations to confirm:
   - All PK columns are `uuid` (not `integer`)
   - All FK columns are `uuid`
   - Junction table columns are `uuid`
   - The filtered unique index for `prompt_versions` (once the markdown import migration is added) is correct

5. Apply migrations and verify seed data populates correctly.

**Note:** Any existing data in a local or dev database will be lost. This is expected — this migration is a breaking change to the schema and must be done on a clean database.

## IStore Interface — No Changes Required

`IStore<T>` is generic and does not specify ID type. Individual store method signatures will be updated to use branded IDs where they currently take `int`, but the interface contract itself is unaffected.
